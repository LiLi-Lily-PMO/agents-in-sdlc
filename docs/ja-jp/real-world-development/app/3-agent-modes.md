最初に小さな機能をプロジェクトに追加しました。より大きな変更には、より確実なプロセスが必要です。GitHub Copilot app は組織の既存の作業フローに沿って動くため、適切な方法で必要な機能を構築できます。ここから数回のレッスンで、Issue から機能を実装し、コードの妥当性と機能の動作を確認して、プロジェクトへのマージまで進める、一般的なエージェント主導の開発プロセスを実践します。

> [!NOTE]
> 機能の作業を続ける間は、同じセッションを使います。通常はファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主な概念に集中するため手順を簡略化しています。

このレッスンでは、次の内容を学びます。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザー Canvas で機能を手動で検証します。

機能の作業を続けながら、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能 PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がカテゴリや発行元でゲームを絞り込めるようにする必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードで決定し、Autopilot で範囲を限定した実装を承認します。

## 背景

AI コーディングエージェントを開発フローに取り入れても、基本は変わりません。むしろ、基本がさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 作業内容を記載した Issue を開きます。
2. 実装する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で確認します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションが成功したら、コードをマージします。

> [!NOTE]
> 具体的な手順はチームや組織によって異なりますが、多くは上記の流れを調整したものです。

この標準的な進め方に従うことで、AI が生成したコードが要件を満たし、手作業で書いたコードと同じレビューのプロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントがどこまで自律的に作業するかを制御します。プロンプト欄の下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントが変更を提案し、次に進む前にユーザーの入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントが入力を待たずに、コード作成、テスト、タスク完了までの反復を自律的に行います。

最初に Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

フィルター機能の作業を始める前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。テンプレートから用意された Issue があるため、新しい Issue を作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

   ![New session ボタンが強調表示された GitHub Copilot app の Issue ビュー](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モード選択で **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで動作しない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチを確認できます。Issue から開始したため、Copilot はすでに機能の依頼をコンテキストとして把握しています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画が Issue の受け入れ条件に合っていることを確認します。カテゴリと発行元によるフィルター、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリの組み合わせや、ゲームが見つからない場合の動作など、不明な点を相談します。

計画には、プロジェクトに既存のツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルター機能の実装とテストに集中し、品質ワークフローを終えた後に PR を作成します。計画に変更が必要な場合は、承認する前に修正を依頼します。後で検証するため、Issue の URL と合意した詳細を記録しておきます。

## Autopilot を明示的に承認する

計画に納得できたら、**Approve and implement this plan** または使用中のバージョンにある同等の選択肢を選びます。承認するとモードも切り替わると決めつけず、実際のモードを確認してください。モード表示が **Autopilot** であることを確認します。

Copilot が実装を開始します。計画に沿って作業を繰り返し、コードを生成してテストを実行します。

> [!NOTE]
> 承認すると実装がすぐに始まる場合があります。必ず先に計画を確認してください。依存関係が不足している、またはポートが競合していると Copilot が報告した場合は、チェック完了と判断する前に環境の問題を解決します。自分が起動したサーバーのみ停止してください。

## 実装をレビューして検証する

ほかのコードと同様に、生成したコードもマージする前にレビューします。コードを確認し、サイトを実行して問題がないか確認します。

1. **Changes** を開き、フィルターの実装とテストを確認します。
2. 結果を Issue と承認した追加要件 (複数カテゴリや発行元の組み合わせなど) と照らし合わせます。既存のリポジトリ指示に従っていることを確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解決し、影響を受けるチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして実行し、ローカルサーバーを再利用する場合があります。テスト対象が前のレッスンのサーバーではなく、この worktree のものであることを確認してください。

## 新機能を確認する

コードに問題がないように見えても、実際に動くでしょうか。前回と同じようにアプリを起動し、ブラウザー Canvas で Web サイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザー Canvas で開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーが開きます。
3. カテゴリを選んで結果が一致することを確認します。フィルターを解除し、発行元を選んで結果が一致することを確認します。
4. カテゴリと発行元のフィルターを組み合わせ、結果を Issue と承認済みの計画と照合します。複数カテゴリに対応している場合は、合意した組み合わせの動作を確認します。
5. ゲームが見つからない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットして、一覧がすべて表示されることを確認します。
6. 確認が終わったら、次のプロンプトで、このセッションのために起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンのためにこのセッションを保持する

まだフィルター機能の PR を作成したり、マージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルター機能のコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションをそのままにしておきます。次のレッスンで同じセッションに戻ります。
